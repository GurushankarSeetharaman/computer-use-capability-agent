# Design Write-up — Computer-Use Automation System

## Architecture

The system has two execution modes that share one core, split at the point where the LLM leaves the loop. **Discovery** takes a natural-language goal and a target, and runs an observe → decide → act loop: the surface adapter perceives the current page, Claude (via tool-calling) decides one action, and the surface adapter acts on it — with the guardrail check happening inside `act()` itself, before anything touches the page — and the step is recorded, repeating until the goal is met or a stop condition (max steps, timeout, stuck) is hit. **Replay** takes a saved artifact and a set of inputs and executes the recorded steps directly against the same surface adapter, with no model in the decision loop at all.

Both modes share the same surface adapter (perceive/act, Playwright-backed), the same guardrail, the same evidence logger, and the same escalation manager — there is exactly one code path from any decision (model or recording) to the live page, and it always passes through policy enforcement.

Discovery produces a raw, noisy transcript (retries, dead ends, the model's own scratchpad reasoning). A separate Compiler pass distills only the successful path into the artifact, so the reusable capability is decoupled from the raw model transcript rather than being the transcript with formatting applied.

Deliberate trade-off: single process, synchronous, CLI-driven, file-based artifact storage (JSON on disk). No queues, no services, no multi-tenant plumbing. This is a scope choice, not an oversight — the interesting problems here are the artifact contract, the error taxonomy, and the safety model, not distributed systems infrastructure that a real deployment would eventually need but that a one-app, one-tenant proof of concept doesn't.

## Artifact schema

The artifact is shaped like a callable capability, not a step list — inputs and outputs are typed and named because that's the actual contract an AI agent invokes (`item_name`, `username`, `password[sensitive]` in, `order_total` out, for example). Each step's target is identified by a `locator`: a `strategy` (role+name, css, xpath, or text) with a `primary` choice and an ordered list of `fallbacks`. Replay tries them in order and logs which tier actually resolved the element — that log is a drift signal for free, with no extra instrumentation, since a capability sliding from the primary tier to its fallbacks over time means the app underneath it changed.

`expected_business_outcomes` lives on the step itself, not bolted on afterward, which forces thinking about "what can legitimately go wrong here" at authoring time rather than as an afterthought. `risk_level` is per-step rather than per-capability, since one capability can legitimately mix safe reads with a single irreversible write.

The schema grew once under contact with the real target: saucedemo's order summary puts the subtotal and the total in sibling text nodes distinguished only by a label prefix (`"Item total: $29.99"` vs. `"Total: $32.39"`), with no ARIA role separating them, and text matching is case-insensitive substring — so `"Total:"` matched both. I added an optional `regex` field to the text locator strategy to disambiguate precisely without baking the current dollar value into the locator — an addition the original schema didn't anticipate, driven by a real failure mode rather than speculative generality.

## Determinism & error handling

The single most important decision in the system is keeping the result contract as three distinct top-level states — `success`, `business_outcome`, `failure` — rather than a success/exception split with error codes bolted on. Conflating "no such record" with a crash is the design mistake this project is explicitly built to avoid, and treating it as a first-class outcome rather than an exception is what keeps a caller from having to guess which one they got.

Locator resolution tries `primary`, then each `fallback` in order. Critically, a tier that matches more than one element is treated as a resolution failure for that tier, not resolved by position — an earlier version used Playwright's `.first`, which silently picks whichever element happens to come first when a locator is ambiguous. I found this live: saucedemo's inventory page has six visually identical "Add to cart" buttons, and the naive role+name locator genuinely matches all six. Under `.first` this would have silently clicked the wrong product on a page where the intended one wasn't first; with strict-match-only, the ambiguity is caught, the tier is recorded as failed with its match count, and the CSS fallback correctly recovers.

I also verified the business-outcome path against a live run rather than trusting the design on paper: replaying the artifact with a deliberately wrong username correctly classifies as `business_outcome` / `invalid_credentials` (matched against saucedemo's "Epic sadface" banner text), not as a generic `failure`. Business outcomes are now screenshotted by default, since "what did the page actually say" is the first question anyone will ask about a disputed result.

## Heterogeneity & multi-tenant

The seam is `perceive()`/`act()`. Locators are stored as semantic role+accessible-name pairs, not raw DOM paths, so a `LegacyWebAdapter` — still exposing an accessibility tree even over frameset/table-based markup — could add a heavier "locate by visible text near a landmark" fallback strategy, and a `DesktopAdapter` could swap Playwright for an OS accessibility API (UI Automation on Windows, AT-SPI on Linux) while exposing the same role+name shape. The artifact schema doesn't change for either; only the adapter does.

For multi-tenant reuse, a capability recorded against one tenant's instance of a vendor product should apply to another tenant's instance of the same product through a thin binding overlay (`tenant_id`, `base_url`, `label_overrides`) layered on top of the same semantic locators — only branding/label differences need overriding, not the recorded flow itself. Drift detection falls out of the same per-tier logging already described above: tracking fallback-tier usage rate per (capability, tenant) pair flags a tenant whose app version has drifted before it causes a hard failure, without any additional tooling.

This isn't purely theoretical for me — I saw a version of it happen within a single app, across repeated discovery runs against the same flow. The agent chose two different CSS fallbacks for the same "add to cart" action (`#add-to-cart-sauce-labs-backpack` in one run, `.inventory_item:has-text('Sauce Labs Backpack') button` in later ones), and my `item_name` parameterization only recognized the first pattern. That's exactly the instability this section is meant to anticipate, showing up before I ever got to a second tenant — see Cuts.

## Escalation & handoff

Three triggers hand control to a human: the discovery agent calling `report_stuck` (or falling silent and calling no tool at all, which is nudged once and then escalated), replay hitting a failure it can't classify, and a step flagged irreversible without a pre-set approval — which the guardrail refuses, and which reaches the human through the same replay-failure path. The design also names a no-progress detector, repeating an action for N steps without advancing; that one is not implemented, and `report_stuck` carries the load instead. The intervention request carries run_id, the capability/goal, the current step, a screenshot, the reason, and a timestamp — enough for a person to act without digging through logs first.

Control transfer is the load-bearing part: automation pauses on the same Playwright `BrowserContext`/page — it is never closed or replaced, which is asserted directly by a test — and exposes an opt-in CDP remote-debugging endpoint (off unless a port is configured, since an open debugging port is itself a control channel into the browser) plus a minimal local operator console with a single Resume button, so a human can attach to and drive the exact session that was already running. Who's in control is a single `control_owner` field on run state, flipped atomically behind a lock, since the console runs on a background thread and genuinely races the discovery/replay loop. On resume, the run re-perceives current state and continues at the *next* step, never by retrying the one that was escalated — retrying a manual action like placing an order could duplicate it. What a human does while in control is logged to the same evidence trail tagged `actor: human`, at navigation granularity: the paused loop polls the page and records where they went, not every click and keystroke. Capturing those would mean instrumenting the page over CDP, and a partial input trace that silently missed events would be worse evidence than an honest record of the pages visited.

Honest limit: this mechanism is proven by unit tests and a `--force-escalate-at-step` flag built for demonstration, not by an organically triggered live refusal — saucedemo stayed within the allowlist across every discovery and replay run I ran today.

## Safety

Guardrail enforcement is a structural mechanism, not a caller convention: the surface adapter takes an `AllowlistConfig` at construction with no default, so there's no way to build one without a policy, and its `act()` checks that policy internally, before the browser is touched, on every single call — meaning neither discovery nor replay can forget to call it, because there's no other path to the page. Two details worth calling out because they're common ways this class of check gets defeated in practice: allowed origins are compared as parsed structures rather than string prefixes (a naive `startswith` check would accept `https://www.saucedemo.com.attacker.example` against an allowlisted `https://www.saucedemo.com`), and route-glob matching is case-sensitive (`fnmatchcase`) so policy behavior can't differ between a developer's machine and CI.

Safe/reversible actions proceed automatically; irreversible actions require an explicit pre-set approval or trigger escalation. Credentials are passed into a discovery run as structured parameters rather than embedded in the natural-language goal, and the redactor is seeded with their values before the first log line is written — closing a real ordering gap where a credential quoted in prose would otherwise reach the log before the redactor learned it from a sensitive-marked field. The same change means the model never sees a credential value at all: it refers to them by placeholder and the runner substitutes at the moment of typing. This decision paid off in a way I didn't anticipate: saucedemo's own accessibility tree echoes the typed password back into a page snapshot (`role='textbox' name='Password' value='<password>'`), and that value was still correctly redacted on write — only because the redactor already knew it going in, not because anything scanned for it after the fact.

Named limit: this is allowlist + risk-tier + redaction, not a full policy engine. There's no per-tenant policy override and no continuous confidence/reliability scoring of artifacts.

## Cuts

Not built: the legacy-web and desktop surface adapters (designed above, not implemented), the multi-tenant binding overlay (no `tenant_id` or `label_overrides` fields exist — what the schema provides is the semantic role+name locator vocabulary that would make such an overlay possible, and there's no second tenant to test it against), and a real operator console (mocked as a bare page with one button — the control-transfer mechanism underneath it is real and tested, the UI around it isn't).

The most concrete cut is parameterization robustness. The `item_name` non-determinism described above — repeated discovery runs choosing different locators for the same action, only one recognized by my templating rule — is a real, evidenced gap, not a hypothetical one. The honest fix is a proper structural locator strategy (matching by visible text near a DOM landmark, the same fallback already named for the legacy-web adapter) rather than a broader regex over observed patterns, since a wider regex would just be fitting the next example I happen to see rather than solving the underlying problem. That's what I'd build next given more time — it's the specific thing standing between "works for one recorded run" and "a capability that's actually reusable across repeated recordings of the same flow," which is a precondition for the multi-tenant story above ever working at all.

Second priority: exercising the escalation path against a real, organically triggered refusal rather than only unit tests and a forced-trigger demo flag.
